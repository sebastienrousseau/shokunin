# SBOM and SLSA build provenance — downstream verification guide

This page documents the **two SBOM formats** and the **SLSA v1.1
Level 3 build provenance** that every `ssg` release ships, and shows
exactly how a downstream consumer (procurement reviewer, SRE,
security analyst) can verify them.

It satisfies issue [#533][issue-533] (`SLSA v1.1 build provenance
and SPDX 3.0 SBOM compliance`) and is referenced from the release
notes auto-generated by `.github/workflows/release.yml`.

## What ships with every release

| Artefact                              | Format                         | Where it lives                                                    |
| ------------------------------------- | ------------------------------ | ----------------------------------------------------------------- |
| Binary / package archives             | `.tar.gz` `.zip` `.deb` `.rpm` `.pkg` `.msi` | GitHub Releases                                          |
| SHA-256 checksum sidecars             | `<file>.sha256`                | GitHub Releases                                                   |
| Detached GPG signatures (optional)    | `<file>.asc`                   | GitHub Releases (only when `GPG_PRIVATE_KEY` secret is configured) |
| **SLSA v1.1 Level 3 provenance**      | `ssg-<tag>.intoto.jsonl`       | GitHub Releases (uploaded by `slsa-github-generator`)             |
| **CycloneDX 1.5 SBOM** (transitive)   | `*.cdx.json`                   | `Scheduled` workflow → `sbom-cyclonedx` artefact (90-day retention) |
| **SPDX 2.3 SBOM** (transitive)        | `ssg.spdx.json`                | `Scheduled` workflow → `sbom-spdx` artefact (90-day retention)    |
| Per-site embedded SBOM                | `sbom.cdx.json`                | At the root of every site SSG builds (`SbomPlugin`)               |

## Verifying SLSA v1.1 provenance

The release pipeline calls the
[`slsa-framework/slsa-github-generator`][slsa-gen] reusable workflow
(pinned at `@v2.1.0` — reusable workflows must be tag-pinned, not
SHA-pinned, because the generator validates `github.workflow_ref`
against the tag to mint a non-falsifiable `buildType`). This emits
a single `ssg-<tag>.intoto.jsonl` covering every primary release
artefact, signed by Sigstore via short-lived GitHub OIDC tokens.

### One-shot verification

```sh
# Install slsa-verifier once (Go is required):
go install github.com/slsa-framework/slsa-verifier/v2/cli/slsa-verifier@v2.7.1

# Or grab a release binary:
#   https://github.com/slsa-framework/slsa-verifier/releases

TAG=v0.0.44   # the release you're inspecting
ART=ssg-${TAG}-x86_64-unknown-linux-gnu.tar.gz

gh release download "$TAG" \
  --repo sebastienrousseau/static-site-generator \
  --pattern "$ART" \
  --pattern '*.intoto.jsonl'

slsa-verifier verify-artifact "$ART" \
  --provenance-path "ssg-${TAG}.intoto.jsonl" \
  --source-uri github.com/sebastienrousseau/static-site-generator \
  --source-tag "$TAG"
```

A successful run prints `PASSED` and the buildType
(`https://slsa-framework.github.io/slsa-github-generator/generator_generic_slsa3.yml@vX.Y.Z`).
Any divergence — wrong source repo, replaced binary, tampered
provenance — causes a non-zero exit.

### What the provenance claims

The minted attestation contains the SLSA v1.1 predicate:

- `subject[].name` — release artefact filename
- `subject[].digest.sha256` — SHA-256 of that artefact
- `predicateType` — `https://slsa.dev/provenance/v1`
- `buildDefinition.buildType` — the SLSA generic generator workflow ref
- `buildDefinition.externalParameters.workflow.ref` — the release tag
- `runDetails.builder.id` — the hosted GitHub runner identity (OIDC-attested)

The runner identity (`runDetails.builder.id`) is non-forgeable —
it is asserted by GitHub's OIDC issuer, not by anything in the
release workflow. That is the Level 3 invariant.

### Post-release self-check

`release.yml`'s `verify-provenance` job re-runs `slsa-verifier
verify-artifact` against the just-published release. A green
release with a red `verify-provenance` job means the attestation
is unusable and the release must be re-cut. This is the regression
gate for issue [#533][issue-533] AC3.

## Verifying SBOMs

### CycloneDX 1.5

```sh
# Schema validation via the official CLI
npx --yes @cyclonedx/cdxgen --validate ssg.cdx.json

# Or via the Python tool (used in tests/sbom_compliance.rs)
pip install cyclonedx-bom
cyclonedx-py --input-file ssg.cdx.json --validate
```

### SPDX 2.3

```sh
# Official SPDX validator (Java)
docker run --rm -v "$PWD:/data" \
  spdx/spdx-online-tools-validator:latest \
  validate /data/ssg.spdx.json

# Or use the JSON Schema directly:
curl -sL https://raw.githubusercontent.com/spdx/spdx-spec/v2.3/schemas/spdx-schema.json \
  -o /tmp/spdx.json
jsonschema --instance ssg.spdx.json /tmp/spdx.json
```

### Why SPDX 2.3 and not 3.0

SPDX 3.0 is a 2024 redesign that switches the document format to
JSON-LD and restructures the data model around "elements". As of
this release, no production-grade Cargo SBOM generator (cargo-sbom,
cargo-cyclonedx, syft) has shipped SPDX 3.0 emission. We ship 2.3
today — the format that NTIA "minimum elements" guidance, EO 14028
SBOM Resource Hub, and the EU CRA all currently accept — and will
upgrade to 3.0 in a follow-up issue when the toolchain catches up.

Until then, consumers who specifically need 3.0 can convert via the
[`spdx-tools`][spdx-tools] reference implementation.

## Regulatory cross-reference

| Requirement                                                                                                  | Artefact that satisfies it                          |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **US EO 14028** §4(e)(vii) — "providing a purchaser a Software Bill of Materials"                            | `ssg.spdx.json` (SPDX 2.3) + `ssg.cdx.json` (CycloneDX 1.5) |
| **US EO 14028** §4(e)(ix) — "attesting to conformity with secure software development practices"             | `ssg-<tag>.intoto.jsonl` (SLSA v1.1 L3, Sigstore-signed) |
| **EU Cyber Resilience Act** Annex I §2(1) — SBOM "in a commonly used and machine-readable format"            | SPDX 2.3 JSON                                       |
| **FedRAMP** SR-3 / SR-4 — supply chain risk management documentation                                         | CycloneDX SBOM + SLSA L3 provenance + reproducible build hash |
| **NIST SSDF** PS.3.2 — "archive and protect each software release"                                           | GitHub Release tag + Sigstore-signed provenance     |
| **SLSA v1.1 Build L3** — non-falsifiable provenance from a hosted, isolated builder                          | `generator_generic_slsa3.yml` reusable workflow + GitHub OIDC |

## Caveats

- The `verify-provenance` job runs **after** the release is
  published. A failure does not prevent the release from existing,
  but it does fail the workflow run, which is the surfaced signal.
- `actions/attest-build-provenance` (GitHub-native attestation)
  continues to run in parallel. The two attestations are
  complementary, not redundant — the GitHub one is verifiable via
  `gh attestation verify`, the SLSA one via `slsa-verifier`. Both
  cover the same subjects.
- SPDX 2.3 generation depends on `cargo-sbom` v0.10. The cache key
  in `scheduled.yml` (`cargo-sbom-0.10`) must be bumped if we
  upgrade the binary, otherwise the cached binary will be reused.
- The container image (`ghcr.io/sebastienrousseau/static-site-generator`)
  is not currently in the SLSA subjects list. Container provenance
  is tracked in a separate follow-up; for now, container consumers
  should pin by digest and use `cosign verify` against the registry.
